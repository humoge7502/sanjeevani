                                               SANJEEVANI
                         3-Member Engineering Workflows & AI-Agent Handoff Specification


 Purpose: Give each team member—and any coding AI/agent—a precise, non-overlapping understanding of
 ownership, interfaces, implementation order, acceptance criteria, Git workflow, and integration responsibilities.

 Project: SANJEEVANI — The Self-Healing Pharma Supply Chain Network

 Core principle: Sense → Verify → Understand → Scenario → Simulate → Optimize → Approve → Execute → Audit
 → Learn.

 Architecture rule: Six disciplined MVP agents implement the required capabilities; do not turn the conceptual 16-role
 roster into 16 independent agents.



 1. NON-NEGOTIABLE TEAM ARCHITECTURE
 The team works in one Git repository. Each member owns a vertical slice, but all three integrate through explicit
 JSON/Pydantic-style contracts. The critical path is one polished end-to-end demo, not three independent subsystems.

     Member 3             Compliance + HITL + SAP execution +      Can we safely execute it?             A5, A6

 Important: A2 combines verification + scenario; A3 combines graph + impact; A4 combines
 inventory/logistics/supplier/optimization; A5 combines compliance + approval; A6 combines audit + learning. This

 4. MEMBER 1 — AI / DATA / GRAPH LEAD
 Mission: Build the upstream intelligence layer. Convert raw signals into a verified disruption, scenario, network impact,
 and machine-readable handoff to Member 2.

 Own: A1 Sensing; A2 Verification & Scenario; A3 Network Impact; synthetic pharma network; event data;
 graph/network reasoning; confidence/provenance; impact report.

 Do NOT own: recovery optimization, SAP execution, approval UI.

 Workflow
 Signals → normalize → classify → verify/deduplicate → confidence/staleness → create scenario → traverse network
 → calculate affected shipments/products → calculate stockout/service/revenue risk → emit Impact contract.

 Implementation order
 1. Create deterministic synthetic 12-node pharma network: suppliers, plants, ports, warehouses, lanes and customers.

 2. Create scripted disruption feeds: Red Sea closure and biologics temperature excursion. Keep all demo inputs
 deterministic/offline.

 3. Implement Sensing Agent: ingestion, normalization, event typing and source metadata.

 4. Implement Verification: confidence, deduplication, freshness/staleness and severity.

 5. Implement Scenario Agent: convert verified event into parameterized 3/10/30-day scenario objects.

 6. Implement Network Impact: graph traversal and affected-node/shipments calculation.

 7. Add impact metrics: revenue-at-risk, stockout probability, service-level risk.

 8. Expose one clean function/API that returns the shared Impact object.

 9. Write unit tests and one integration fixture consumed by Member 2.

 Acceptance criteria
 ✓ Given the seeded scenario, the system detects the intended event deterministically.

 ✓ Verification returns confidence, provenance and freshness fields.

 ✓ Network impact is reproducible from the same input.

 ✓ Output validates against the shared Impact schema.

 ✓ Member 2 can run your module without importing private internals.

 ✓ Every important number shown in the UI can be traced to source data or a deterministic calculation.

 AI-agent instruction
 If you are an AI coding agent working for Member 1: inspect the existing repository before creating files; preserve
 existing working code; implement only Member 1 ownership; do not redesign the architecture; do not add agents;
 do not add real SAP integrations; create tests for every public contract; document every interface you expose;
 finish with exact run/test commands and a list of files changed.

 5. MEMBER 2 — DIGITAL TWIN / OPTIMIZATION LEAD
 Mission: Take Member 1's quantified impact and determine the best recovery plan using deterministic simulation and
 mathematical optimization.

 Own: A4 Recovery; SimPy digital twin; three recovery strategies; Pyomo + HiGHS MILP; OR-Tools routing;
 cost/service/resilience/temperature-risk calculations.

 Do NOT own: event sensing, final compliance gate, SAP API implementation, frontend.

 Workflow
 Impact → construct disrupted network state → replay baseline → simulate WAIT / REROUTE VIA MUMBAI + AIR /
 EMERGENCY SOURCE → calculate KPIs → optimize → select best feasible plan → emit RecoveryPlan.

 Implementation order
 1. Consume Member 1's Impact contract using a fixture first; do not wait for live integration.

 2. Implement a deterministic SimPy digital twin for the 12-node network.

 3. Implement baseline 'WAIT' strategy.

 4. Implement 'REROUTE VIA MUMBAI + AIR'.

 5. Implement 'EMERGENCY SOURCE'.

 6. Define objective terms: recovery cost, service level, resilience score and temperature risk.

 7. Implement Pyomo/HiGHS optimization with explicit constraints and bounds. The LLM must not perform the math.

 8. Add OR-Tools routing only where it materially supports the demo route decision.

 9. Return a ranked strategy table plus one RecoveryPlan object.

 10. Add deterministic tests for feasibility, objective calculation and repeatability.

 Acceptance criteria
 ✓ All three strategies run from the same scenario input.

 ✓ Repeated runs with the same seed produce the same results.

 ✓ The optimizer never violates hard constraints.

 ✓ The recommended plan validates against the shared RecoveryPlan schema.

 ✓ The strategy table contains enough data for the UI to render cost/service/risk/resilience.

 ✓ No LLM-generated number is treated as authoritative when a deterministic engine can calculate it.

 AI-agent instruction
 If you are an AI coding agent working for Member 2: first inspect Member 1's contract and current repository.
 Build the simulation/optimization layer against the contract fixture. Keep solver logic deterministic and testable.
 Never silently change upstream schemas. Do not add GNNs, real SAP APIs, model training, or extra agents.
 Report solver assumptions, constraints, objective terms, test commands, and integration points when finished.

 6. MEMBER 3 — SAP / GOVERNANCE / UI LEAD
 Mission: Turn the optimized recovery plan into a governed business action: validate it, ask for human approval,
 execute through SAP-shaped mocks, and produce an auditable result.

 Own: A5 Compliance + HITL; CAP mocks for IBP/TM/Ariba; execution receipts; A6 Audit + Learning; React/Vite
 dashboard; approval screen; demo orchestration API.

 Do NOT own: core optimization mathematics or upstream event detection.

 Workflow
 RecoveryPlan → policy validation → compliance checks → risk tier → approval card → human approval →
 SAP-shaped execution → receipts → audit ledger → outcome/learning panel.

 Implementation order
 1. Create backend API/orchestrator that can consume a RecoveryPlan fixture.

 2. Implement policy engine: budget caps, parameter bounds, sanctions/trade/GDP-style checks and approval rules.

 3. Implement approval state machine; consequential actions must pause for human approval.

 4. Implement CAP Node.js mocks shaped like IBP scenario, TM freight and Ariba risk/procurement contracts.

 5. Implement execution client with transactional sequencing and visible receipts.

 6. Implement append-only decision ledger: event, reasoning metadata, scenario, recommendation, approval, action
 and outcome.

 7. Implement learning/outcome view comparing predicted vs actual and showing a recalibration notice; do not pretend
 to have autonomous model retraining in MVP.

 8. Build dashboard: loop HUD, network map, impact KPIs, strategy table, compliance panel, approval card, execution
 receipts, audit/learning.

 9. Add offline demo mode and one-command reset.

 10. Integrate all three members and freeze the demo path.

 Acceptance criteria
 ✓ Every execution is blocked until the required approval is present.

 ✓ Compliance failure prevents execution and explains why.

 ✓ IBP/TM/Ariba mocks return deterministic receipts.

 ✓ Audit record exists for every major loop stage.

 ✓ Frontend can render the complete journey from one seeded scenario.

 ✓ Demo runs without venue Wi-Fi or live APIs.

 AI-agent instruction
 If you are an AI coding agent working for Member 3: inspect the repository and shared RecoveryPlan contract
 first. Preserve the governance boundary. Build API-faithful mocks rather than real SAP tenant integrations. Never
 allow a UI click to bypass policy validation. Keep the demo deterministic/offline. Do not add extra agents or
 features. Return exact start/reset/demo commands and identify every mock boundary clearly.

 loop.


 8. GIT / COLLABORATION RULES
 ✓ main is always runnable.

 ✓ Each member works on a dedicated branch: member1-ai, member2-optimization, member3-sap-ui.

 ✓ Pull/rebase or merge the latest main before integration work.

 ✓ Small commits; one logical change per commit.

 ✓ Never commit secrets, API keys, .env files, generated databases or huge model files.

 10. DEFINITION OF DONE
 ✓ Functional: one complete deterministic scenario runs from signal to audit.

 ✓ Governed: no consequential SAP-shaped action bypasses policy + human approval.

 ✓ Explainable: every recommendation has visible reasons and numerical evidence.

 ✓ Reproducible: seeded data and offline mode produce the same demo result.

 ✓ Integrated: all shared contracts validate automatically.

 ✓ Demoable: presenter can reset the system and rerun the scenario quickly.

 ✓ Defensible: team can explain what is real, what is simulated, and what is mocked.

 ✓ Scope-safe: no real tenant integration, no trained forecasting model, no GNN cascade, no extra agents in MVP.
